# OPT-02 — 页面缓存的过期与恢复

2026-10-08 本地实现；变更与测试结果记在 [开发修改记录](development-change-log.md) 第 16 节。第 24 节补齐空成功的验收与同 token 下贡献数变化的范围。只改 Streamlit 前端，API 和数据库不变；部署另行安排。

旧版有三个问题：

- 首页课程总数（`_ready_info`）和 Co-op 预览（`_coop_teaser_cache`）一旦加载失败，空结果会在这个标签页里一直保留。API 冷启动的 70–100 秒里 `/ready` 返回 503，这段时间打开页面的人，课程总数要等重新加载页面才会出现；
- 培养方案列表和课程表失败时完全不缓存。落地页一次 rerun 里有三处读项目列表，后端卡住时每次 rerun 都要依次等超时（每次 8 秒）；
- 成功的结果永不过期。另外，Co-op 预览按访客等级裁剪，缓存却不分身份：登出或换账号后，还会沿用上一个身份拿到的列表。

## 现在的规则

四处缓存都改用 `app/view_cache.py`：

| 缓存 | 接口 | 范围 |
|---|---|---|
| `_ready_info` | GET /ready | 公开 |
| `_coop_teaser_cache` | GET /coop | 每个会话 token＋贡献数一个范围，游客固定一个范围 |
| `_programs_cache` | GET /programs | 公开 |
| `_curriculum_cache[program_id]` | GET /programs/{id} | 公开 |

- 成功的结果用 5 分钟（`SUCCESS_TTL_SECONDS`），之后下一次读取时重新获取。
- 失败记 30 秒（`FAILURE_TTL_SECONDS`）。这段时间里的 rerun 不再发同一个请求，页面上显示的仍是失败的状态（区块不显示，或者项目页的错误提示）；过了 30 秒的第一次读取会重试。Streamlit 只在用户操作时 rerun，所以恢复要等用户下一次操作，或者点刷新按钮。
- 重新获取失败、并且失败可能自己恢复（`transient()`：408、429、5xx，包括连接失败和下面说的非 JSON 响应）时，如果同一范围之前成功过，继续显示上次成功的内容，30 秒后再试；没有成功过才把错误交给页面。
- 明确的答复（401、403、404 等其他 4xx）不回退：上次成功的内容随之丢掉，错误直接交给页面。比如同步后某个项目被删掉，课程表页显示「无法加载课程表」，而不是一直显示旧课程表；会话 token 过期以后，Co-op 预览的下一次获取收到 401，从那时起不再显示会员看到的列表。在那之前，缓存里的列表最多还会显示 5 分钟。
- 记录绝不会给另一个范围用，失败时的回退也不行。Co-op 预览的范围为 `session:<token 的 SHA-256>:c<贡献数>`，记录里不另存 token；换 token 或本地已知贡献数变化就是新的范围，下一次预览重新获取，旧范围的内容也不作回退。采用完整贡献数，不在客户端复制服务端等级规则；2→3 同样重取。贡献数缺键按 0，存在但不是非负精确 int（bool 不算）时为 `c?`，不与任何真实计数共用；游客忽略贡献数。登出时 `logout()` 还会直接删掉这条记录。
- 只缓存 `ApiError`，外加一种情况：2xx 响应里不是 JSON（代理或维护页面）时，`fetch()` 抛出的 `ValueError` 按 502 的 `ApiError`（`error_type="invalid_response"`）处理。以前缓存的成功结果从不重新获取，这种响应只可能出现在标签页第一次加载时；现在 5 分钟后会重新获取，不处理的话每个页面都会变成 traceback。其他异常照旧抛出，也不缓存。
- 第一次失败时，页面拿到的是请求本身的 `ApiError`，和以前一样。之后 30 秒内重复显示的，是按状态码、提示文字和错误类型重新构造的 `ApiError`：会话里不保留原来的异常对象（避免 traceback 一直留在内存里），Retry-After 秒数也不再带上，因为到第二次显示时那个倒计时已经不准了。
- 时钟用 `time.monotonic`；测试替换 `view_cache.clock`，不用真的等待。

落地页有区块因为可能自己恢复的原因加载不了时，显示一行说明，告诉用户稍后再操作会重新获取，也可以点侧边栏的「🔄 刷新页面内容」。明确的答复（比如会话过期时 `/coop` 的 401）只隐藏区块，不说稍后会重试，因为重试也不会成功。项目列表、Co-op 列表为空但加载成功时，不算缺内容。

某次运行里只要有读取因为重新获取失败而显示了上次的成功结果（`begin_run()` 在每次运行开始时清零，`served_fallback()` 判断），页面结尾就在侧边栏刷新按钮下面显示一行「有些内容这次没能更新，显示的是上次加载的版本；稍后再操作页面时会再试。」这样刷新失败时不会悄无声息，用户不会以为内容已经是最新的。说明不写有多旧：故障持续多久，回退的内容就旧多久。

200 响应但内容的格式不对（比如 `/ready` 返回的不是对象、`/coop` 返回的不是列表）算作成功，照样缓存 5 分钟；页面按原来的写法处理：hero 显示不带数字的文案，区块不显示，不另外提示。

## 刷新按钮

侧边栏每个页面都有「🔄 刷新页面内容」。它的 `on_click` 回调把上面所有记录标成过期（`expire_all()`），所以点击后的这一次运行里，每个缓存读取都会重新获取，hero 也一样。上次成功的内容留着，用来作失败时的回退，以及比较课程表里的方案。

刷新只针对这些 GET。回调本身不动聊天历史、待发的问题和各组件的选择；它引起的重新获取只在某个项目的方案变了时清除该项目的方案选择（见下一节），方案没变时选择保留。点击后的 rerun 不会重发提问、Co-op 投稿或回答评价，登录、登出也不会；测试在真实页面上逐一核对过这几种情况。

## 课程表与方案选择

方案选择（`program-plan-{program_id}`）沿用原来的规则：版本变了必须重新选择，绝不悄悄沿用。课程表重新获取到的 `plans` 和上次加载的不完全相同（内容、增删或顺序有变）时，清除这个项目的方案选择，并在课程表页面提示一次「这个项目的版本化方案有更新……请重新选择」。相同则保留选择；只有课程表其他字段（名称、课程行）变了，也保留。没有可比的上次结果、却有选择时，也清除。没有选择时（值是 None）什么也不做，也不提示：真实的 Streamlit 会把未选择的选择框登记成 None，所以「键存在」不等于「选过」。

「清除」是把这个键**设成 None**，不是删掉。删掉的键不会通知浏览器，浏览器里的选择框继续显示旧选项，下一次 rerun 时又把它送回来（按显示文字匹配，同一范围的新版本会被选中），页面说「已清除」，实际却悄悄沿用了旧选择。设成 None 之后 Streamlit 会让浏览器里的选择框一起复位，显示「请明确选择；不默认最新版本」（同一句话也作为 placeholder 传给选择框）。这个问题只在真实浏览器里出现，AppTest 读的是服务端状态，看不出来；第 16 批审查者在浏览器里复现过，修复后又在浏览器里核对过两条路径（5 分钟后重新获取、项目刷新按钮）。同样的改法也用在：选择框之前发现旧选择已不在可用方案里时、方案分享链接清除或替换选择时（`clear_plan_link_selection`、`consume_plan_selection`、`deep_links._evict_family`、链接暂时无法核对时）。这些都发生在这一次运行创建选择框之前；之后再设会触发 Streamlit 的异常。

L（10-21）起，这些选择去过别的页面以后还在：培养方案页每个项目的方案选择，以及搜索页的项目选择（`chat_program_id`）和方案选择（`chat_plan_id`）。原来 Streamlit 会删掉一轮里没渲染的组件的状态，所以从课程表点「查看」去搜索页再回来，选择就没了。现在 `state_manager.keep_choices()` 在每一轮开头、任何组件之前把这几个键原样赋值一次，这是 Streamlit 文档里多页面保留组件状态的写法。上面的清除规则都照旧，清除都是设成 None，所以不会被旧值顶回来；回到页面时重新获取到的方案变了，照样清除并提示。登出和换账号时，`clear_choices()` 把这几个选择都设成 None。

课程表页面原来的「刷新方案及政策证据」按钮不变：它删掉当前项目的缓存，并且无条件清除选择（同样是设成 None），因为是用户自己要求的，不再另外提示「方案有更新」。之后重新获取失败时显示错误，不回退到之前的课程表。政策证据本来就不缓存，每次按所选方案请求。

## 不在本批范围

- Co-op 页面本身的列表、课程详情面板仍是每次运行都请求，没有缓存，也就没有过期的问题。
- 分享链接里的 `?course=` 和方案链接自己的 GET 也不走缓存：确定结果之前，每次 rerun 都请求一次，后端卡住时每次最多等 8 秒。`?program=` 走缓存的项目列表，失败记 30 秒。
- 聊天页的项目选择框（`chat_program_id`）在所选项目已不在列表里时仍是删掉键（原有行为，项目被删的情况很少），没有改成设成 None。
- 不做后台轮询：页面不会自己 rerun 来重试。
- 审核员发布旧投稿后，客户端不一定已经知道新的贡献数；它在重新登录、刷新触发 cookie 恢复的 `/auth/me` 或下一次投稿响应中获取新计数，此前预览仍最多沿用 5 分钟，手动「🔄 刷新页面内容」可以重取。不会每次 rerun 都请求 `/auth/me`。sidebar 的贡献数显示照旧在登录和投稿时更新。新的 pending 投稿本身不会即时增加贡献数，必须以响应中的服务端计数为准。
- 范围只跟着这个标签页知道的变化走：登录、cookie 恢复、投稿响应。下面这些变化，都要到下一次获取才体现，最多等 5 分钟，或者点「🔄 刷新页面内容」：
  - 审核员发布；
  - 别的标签页里的投稿或登录（贡献数是每个标签页各记各的）；
  - token 对应的账号被删（这时 `/coop` 按 0 级回 200，不是 401）；
  - token 过期。

  什么也不会泄露：每次获取都以服务端为准，同一个用户只看到替自己取的数据。
- 5 分钟和 30 秒是经验值，没有按真实流量测过；需要调整时只改 `app/view_cache.py` 里的两个常量。
- API 没有提供数据版本号，所以成功的缓存只能按时间过期，不能按数据版本失效。
