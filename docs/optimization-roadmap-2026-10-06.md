## 2. 先修复：安全与验收可信度

### FIX-01 — 聊天错误对外脱敏

**依据**：[api/routes/chat.py](../api/routes/chat.py) 在 GeminiError 与通用异常分支把异常字符串写进 NDJSON `error.detail`；Gemini 包装器也会保留上游异常文本。离线替身中的假凭证字符串能够出现在客户端响应里。这证明路径会透出异常内容，不证明真实密钥已经泄漏。

**建议修改**：

- 客户端只收到固定、安全的错误提示与有限错误类型；可用 request ID 关联诊断，不返回上游 URL、响应正文、凭证或 traceback。
- 同时审查服务器错误日志，不能只把泄漏从响应挪进日志。
- 继续保留部分回答、明确未完整结束，不自动重试、不绑定反馈凭证。

**涉及文件**：[api/routes/chat.py](../api/routes/chat.py)、[llm/gemini_client.py](../llm/gemini_client.py)、[app/api_client.py](../app/api_client.py)、[app/streamlit_app.py](../app/streamlit_app.py)。

**验收**：模拟异常含假凭证、URL、请求正文时，响应和受检日志均不透出；流中断后部分文字仍可查看、无反馈凭证、rerun 不重复 POST。扩展 `test_api_chat.py`、`test_gemini_client.py`、`test_streamlit_app.py` 和相关反馈回归。

### FIX-02 — 回答评测必须区分失败、未完成和通过

**依据**：[scripts/eval_answers_live.py](../scripts/eval_answers_live.py) 的退出码只检查回答硬失败，不检查调用错误。本轮离线复现：5 次调用／5 个错误／0 条已评分回答，仍返回 `exit 0`；对同一报告执行 `--rescore` 也返回 0。

**建议修改**：

- 报告分别记录计划、尝试、完成、失败和未执行数量；模型失败不能从验收分母消失。
- 非 dry-run 的零样本、调用失败、预算导致的未完成，不得标成完整通过；部分报告仍保留，明确状态和原因。
- 校验 `--runs`、`--max-calls` 等参数；dry-run 的零模型调用是独立模式，不混进质量通过率。
- `--rescore` 只更新判分，不能抹掉原运行错误或把失败运行变成通过。

**涉及文件**：[scripts/eval_answers_live.py](../scripts/eval_answers_live.py)、[eval/answer_checks.py](../eval/answer_checks.py)、[tests/test_eval_answers_live.py](../tests/test_eval_answers_live.py)。

**验收**：全失败、部分失败、零样本、预算提前耗尽、非法参数、dry-run 和 rescore 都有独立断言；只有约定的完整成功运行才返回成功状态。纯离线 MockTransport 与假模型即可验证。

### FIX-03 — 判分限定到相关句子、字段和来源

**依据**：[eval/answer_checks.py](../eval/answer_checks.py) 的 `SENTENCE` 不按英文句号分句，`INSTRUCTOR` 则检查整篇答案。

已复现的两个负例：

- `The workload is estimated at 12 hours a week. Reviews report a difficulty of 4.0/5.`：前句的 estimated 让后句错误的数值归因也被判为估计。
- `Ask your professor about prerequisites. RateMyProfessors reviews say this course is easy.`：无关的 professor 被当作评价归给了教师，硬检查不报错。

**建议修改**：正确处理中英文句界、数字小数点和缩写；估计提示只限定相关数值或分句。RMP 的教师归属及“可能关于其他课”提示须关联实际评价陈述，不能由其他段落的关键词替代。后续多课判分保留课程／字段身份，避免相同数字互相污染。

**涉及文件**：[eval/answer_checks.py](../eval/answer_checks.py)、[scripts/eval_answers_live.py](../scripts/eval_answers_live.py)、[tests/test_answer_checks.py](../tests/test_answer_checks.py)。

**验收**：上述负例报错；真正合格的中英回答不误报。补多句、跨段、多课同数值及小数点回归。检查器仍只是人工审阅辅助，不升级成回答事实正确性的证明。

### FIX-04 — 回答渲染过滤与长输入耗时专项

**依据**：[开发修改记录第 12 批](development-change-log.md) 已记录三类未处理问题：渲染器解码后的网址、Streamlit 指令再次渲染标签、重复过滤／正则在部分长输入上呈平方级耗时。当前白名单不能作为安全边界。

**建议修改**：单独设计有界、可审查的渲染流程，明确允许的官方链接和其余文字的处理方式。单遍方案是候选，不在完成验证前宣称线性或不可绕过；不要只继续叠加正则。

**涉及文件**：[app/answer_evidence_view.py](../app/answer_evidence_view.py)、[app/streamlit_app.py](../app/streamlit_app.py)、[tests/test_answer_evidence_view.py](../tests/test_answer_evidence_view.py)。

**验收**：真实目标渲染器检查链接、图片、解码及指令；纯解析器测试作为补充。覆盖跨 chunk、历史与实时一致、普通格式兼容、长输入耗时和长度／事件预算。明确可能牺牲的 Markdown 语法，不以 CommonMark 单独通过替代 Streamlit 浏览器验收。

## 3. 六项后续优化

### OPT-01 — 私有导出统一安全契约

**现状**：[scripts/export_query_log.py](../scripts/export_query_log.py) 使用普通连接、`SELECT *`，默认写 `eval/query_log_export.jsonl` 并覆盖已有文件；该默认路径未被 Git 忽略。相较之下，反馈候选导出已有更严格的只读和原文开关。这里是误创建数据库、误覆盖或误提交私有原文的风险，不是已经发生泄露的结论。

**第一步**：先把旧查询导出对齐 [反馈导出契约](feedback-review-export.md)，不新增生产采集字段。

- 必须显式指定已存在的数据库，采用只读连接和稳定读取快照；拼错路径不创建空库。
- 默认仅输出有限统计；原文导出须显式确认，输出到受控私有位置并避免覆盖。
- 清楚区分 eval、未标记与未知来源；未标记不等于真人。
- 审核默认路径与 Git 忽略规则，同时提醒 Git 忽略不能替代访问控制、脱敏或留存治理。

**验收**：临时库验证无 DML／schema 改动、不创建缺失 DB、不覆盖已有输出；默认结果无查询原文、账号和凭证。统计分母与来源分组可核对。

### OPT-02 — 首页缓存失效与服务恢复体验

**现状**：[app/streamlit_app.py](../app/streamlit_app.py) 的 `_ready_info` 可缓存失败的 `{}`；[app/discover_view.py](../app/discover_view.py) 的 `_coop_teaser_cache` 可缓存失败的 `[]`。同一会话后续 rerun 不会再取这些内容。项目／课程表的成功缓存也需要明确失效策略。

**第一步**：只处理只读内容的缓存恢复。

- 失败缓存设置短有效期，避免每次 rerun 都卡在失败请求，也避免永久隐藏已恢复内容。
- 成功缓存按期限或数据 revision 失效；提供显式“刷新内容”入口。
- 涉及登录态的数据明确缓存范围与切换行为，不能跨身份复用私有结果。
- 缓存刷新不得重放聊天、Co-op 投稿或投票。

**涉及文件**：`app/streamlit_app.py`、`app/discover_view.py`、`app/program_view.py`；对应布局、发现页和状态测试。

**验收**：模拟时钟和“先失败、后恢复”服务，内容能够恢复；有效缓存期间不重复 GET；刷新和登录态切换没有重复 POST，也不展示旧身份数据。

### OPT-03 — 统一数据覆盖、冲突与来源报告

**目标**：回答“下一批到底补哪些数据”，而不只知道总课程数。

**第一步**：做显式副本上的只读审计器，默认只输出汇总，不改课程或来源。

- 按院系／字段汇总缺失、有效目录快照、名称不一致、数值冲突、先修解析状态。
- 区分缺失、抽取估计、存在来源、来源关联一致和人工核对；不能把 hash 或 `source_checked` 自动等同于官方正确或当前适用。
- 抓取日期未知仍写未知，不用导入时间或文件时间代替；按年度／范围统计先修和培养方案，不把 partial 计作完整。
- 后续用经授权、去噪后的真实查询热度选 RMP 富化对象，先补高需求课程，不做无依据全量扩充。

**可复用入口**：[rag/answer_evidence.py](../rag/answer_evidence.py)、[scripts/repair_course_names.py](../scripts/repair_course_names.py)、[scripts/release_preflight.py](../scripts/release_preflight.py)、既有来源审计器。

**验收**：每类计数可回溯到明确分母与规则；坏 JSON、缺 schema、无来源、重复代码、冲突、未知日期和 partial 各有夹具。无写入、无网络、默认无用户原文；报告能区分“未检查”和“检查后没有问题”。

### OPT-04 — 结构化先修与精确方案接入聊天

**现状**：课程详情通过 [api/routes/course.py](../api/routes/course.py) 返回年度先修文档；[rag/answer_evidence.py](../rag/answer_evidence.py) 与 v4 prompt 仍主要传先修代码列表。`ChatRequest` 只有项目家族 `program_id`，没有精确方案身份／revision；聊天的项目选择不替学生选校区、年度或路径。

**第一步**：先把结构化先修接成有来源的解释，再逐步接精确培养方案。

- 学生显式选定 Boston／Catalog 年度／普通、Align 或 Bridge 路径；春秋入学季不能替代 Catalog 年度。
- 按相同课程、年度和选定方案读取有效文档，保留 AND／OR、条件和未解析原文。
- 不确定适用范围时澄清，不自动选择同前缀第一份方案；revision 不一致不能沿用旧成功内容。
- 第一版只解释规则、列出有限匹配或需要核实的缺项，不自动判断个人毕业、转学分批准、跨组计入或实际开课。

**涉及文件**：`api/models.py`、`api/routes/chat.py`、`db/course_requisite_repository.py`、`db/program_plan_repository.py`、`rag/answer_evidence.py`、`llm/prompts/chat_v4.py`、`app/program_plan_view.py`。

**验收**：同年度读取正确；跨年度、路径歧义、过期 revision、缺文档、partial、unparsed 均明确提示。AND／OR 不被压成“全部必修”，条件／批准不被计算成已获资格。先用临时库和替身模型验证，再另行做真实回答抽查。

### OPT-05 — 查询名称映射与歧义澄清

**现状**：`/search` 与 `/chat` 都以 `llm_fn=None` 调用 [extract_filters_adaptive](../llm/query_filter_extractor.py)。但现有 hook 只是“专业名称 → 代码前缀”映射，不能直接解决否定、多条件或所有复杂查询。

**第一步**：补确定性的中英文名称映射和歧义用例，不立即给每个查询增加模型调用。

- 区分学生所属项目、课程院系前缀和项目允许的跨院系课程；不能仅凭“我是 CS 专业”就认定所有合法候选必须是 CS 代码。
- 项目选择、问题里的名称和明确课程代码冲突时先澄清，保留用户否定／比较意图。
- 如确需模型兜底，默认关闭，限定触发条件、允许值、超时和预算；失败不静默丢掉用户明确限制。
- 使用既有固定评测定位增益，不承诺接上 hook 就提高召回，也不借此做真实分布门控重校准。

**涉及文件**：`llm/query_filter_extractor.py`、`schemas/query_filter.py`、`api/routes/search.py`、`api/routes/chat.py`、`tests/test_query_filter_extractor.py` 和检索契约测试。

**验收**：既有明确代码查询不退化；中英文全称、模糊专业名、跨院系、否定、冲突及模型失败都有回归。配置关闭时无额外调用；配置开启的成本和效果只能用独立授权的实际测量说明。

### OPT-06 — 分层评测与完整使用链路

**现状**：[scripts/eval_answers_live.py](../scripts/eval_answers_live.py) 默认五题，直接从 GET 课程详情构造预先指定的候选证据，再调模型；可测提示词与回答，但不能单独证明真实 `/chat` 检索、历史和 UI 全链路正确。

**第一步**：在 FIX-02／03 完成后，分开维护三层证据。

1. 纯函数／契约：来源投影、判分、解析、错误状态，全部离线。
2. API／UI 联动：临时库和模型替身，覆盖实际检索 → prompt → NDJSON → 展示／历史／反馈。
3. 真实回答与真实用户：授权后运行，明确调用预算、数据权限和人工审阅；不拿替身结果替代这一层。

**补充场景**：多轮指代、多课比较、筛选排除、无结果、项目歧义、年度／路径、来源冲突、未解析规则、中英回答、断流、恢复及不重复提交。

**报告要求**：注明代码／prompt／数据或索引身份、用例版本、后端配置、计划与实际分母、失败状态。历史 capped 指标与标准指标分开解释；修正 [eval dashboard](../app/eval_dashboard.py) 时，缺指标显示未知，不默认补 0 或把不可比配置连成趋势。

**验收**：完整请求在同一输入下可核对检索与展示证据；所有失败仍进入对应分母；局部脚本成功不自动成为发布许可。原文评测产物保持私有，人工标签仍需审核，不自动成为 ground truth。

## 4. 并行准备与暂缓项

### 真实用户闭环：并行准备，不代用户执行

- deep links、反馈关联和评测工具已经有实现，不重复从零开发同一入口；先核实最新版本的真实可用状态。
- 小范围试用关注“能否找到课程、理解依据、做出比较、愿意回来用”，不只看测试数或访问次数。
- 分发消息、真实 Google 登录／刷新、生产启用保存和读取真实用户数据，需要本人参与或另行明确授权。
- 保存期限、访问控制、备份和导出治理先确认。反馈凭证七天过期不等于数据七天删除。
- 未带 `X-Eval-Run` 不证明真人；先区分来源并人工去噪，再构建真实分布评测、重校准门控。

### 性能：先定位真实等待，再选择实现

- 分开测检索耗时、首字等待、完整回答耗时、渲染成本和失败／繁忙率；query_log 的检索耗时不能当聊天总耗时。
- FIX-04 的长文本渲染与请求／流事件预算可先本地验证。真实断连后的模型计算是否回收，不能仅由 ASGI lease 释放推定，见 [请求门禁边界](request-admission.md)。
- static-shape 是后续候选，不是已证实的加速方案；NAS／真实后端测试要固定依赖、数据、模型和索引，并先确认目标与运行权限。
- 不重试已经实测否决的 reranker 512→256，也不从合成 profiler 的时长挑生产优化赢家。

### 暂不优先扩大功能面

完整学期规划器、个人毕业资格、全量 RMP 富化、多 worker／分布式配额，不作为下一批默认任务。先有完整适用证据、实际需求或容量瓶颈，再分别立项。尤其不能把当前 partial 培养方案浏览层包装成可靠个人排课保证。

## 5. 建议推进顺序与统一验收

### 分批顺序

1. FIX-01 → FIX-02 → FIX-03；同时把最新三笔提交的改动与验证补进主修改日志。FIX-04 保留为单独渲染专项，不在小修中混入大改。
2. OPT-01 → OPT-02：两个范围清楚的小批次，先保护私有数据，再改善恢复体验。
3. OPT-03：形成明确的数据缺口清单，决定下一批补哪门课、哪个字段。
4. OPT-04：先接结构化先修解释，再接精确方案上下文；每段独立验证。
5. OPT-05：先确定性映射，再根据固定评测决定是否启用受控模型兜底。
6. OPT-06 分段配套推进：每完成一批补对应联动回归；扩大真实评测须另行授权。

真实用户试用准备贯穿上述步骤，不必等所有功能全部做完。存在安全或数据权限问题时，先明确试用范围和发布门槛，不默认开放生产。
